# ADR-0009: 必要な知能レベルで処理経路を分ける

## Status

Accepted

## Context

旅行記が増えるほど、抽出・集計・再生成をすべてCodexへ渡す運用は、利用枠、待ち時間、再現性の面で不利になる。一方、曖昧な歴史解釈、構造設計、UX設計、実装判断まで小規模なローカルLLMへ任せると、品質確認の負担が大きい。

また、「単純処理」にはLLM自体が不要なものが多い。パース、ハッシュ、重複排除、参照整合性、Projection生成を確率的なモデルへ渡すと、同じ入力から同じ結果を得にくくなる。

## Decision

処理は、必要な知能と不確実性に応じて次の3段階へ振り分ける。

| 段階 | 標準手段 | 対象 |
| --- | --- | --- |
| 0. Deterministic | TypeScriptなどのローカルコード | パース、ハッシュ、集計、重複排除、ID・参照検証、Atlas・Projection生成、テスト |
| 1. Local AI | Ollama。現在の既定は`qwen3.5:9b` | Claim・Entity・Place候補抽出、分類、要約、正規化、Topic候補の一次生成 |
| 2. Intelligent work | Codex | 設計、実装、リファクタリング、デバッグ、UX、学際的統合、外部資料の照合、最終レビュー |

常に段階0で表現できるかを先に判断し、必要な場合だけ段階1を使う。段階1の結果が品質基準を満たさない場合、または人間と協働する知的生産そのものが目的の場合に段階2へ進む。

Codex CLIは大量旅行記の標準抽出経路にしない。ローカルLLMが、単一Passageまで分割しても構造化出力を完了できない、根拠範囲を保持できない、または評価基準を継続して下回る場合の明示的な昇格先とする。

## Quality gates

ローカルLLMの結果はDraftであり、次を満たしてから後段へ渡す。

- JSON Schemaを満たす。
- Claimから原文Evidenceへ戻れる。
- 未知のDocument、Passage、Spot IDを参照しない。
- 入力件数と成功・失敗・再利用件数を記録する。
- 失敗したバッチだけを再実行できる。
- Reviewed Assertionや確認済み座標へ自動昇格しない。

品質ゲートを満たさない出力は、Codexへ無条件で全件再送しない。まずプロンプト、バッチ境界、決定的な後処理で解消できるかを確認し、解消できない範囲だけを昇格する。

## Codex usage policy

- 通常の実装とレビューは中程度の推論を標準とする。
- 高い推論は、コア構造の変更、複数の史料・異説の統合、難しい不具合に限定する。
- 対象ファイルと検証コマンドを絞り、途中では関連テスト、節目で全体テストを実行する。
- 長期タスクは工程ごとに分け、正本・決定事項・次の作業をリポジトリ内文書で引き継ぐ。
- Codexの利用枠やトークン量をデータモデルへ持ち込まず、運用上の観測値として扱う。

## Consequences

- 大量処理の費用とCodex利用量を抑えやすい。
- 決定的処理の再現性が上がる。
- ローカルLLMの能力不足を設計判断や表示品質へ波及させない。
- プロバイダーは交換可能なまま維持される。
- 品質ゲートと部分昇格の実装・運用が必要になる。

この判断は保存場所をローカルに固定しない。将来別のローカルモデルやサーバーモデルを使う場合も、同じ段階と品質ゲートに従う。
