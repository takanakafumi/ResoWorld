# AIモデル選択・タスク配分ガイドライン（モデル進化対応版）

## 目的

このドキュメントは、ResoWorld の開発および日々のフィールドワーク記録（旅行記・考察）の取り込みにおいて、**作業品質（[AGENTS.md](../AGENTS.md) の不変条件）を維持しつつ、コスト・待ち時間・リソース消費を最適化するモデル選択基準**を定める。

本ガイドラインは [ADR-0009: 必要な知能レベルで処理経路を分ける](./decisions/0009-route-processing-by-required-intelligence.md) の原則をクラウドエージェント・マルチモデル環境へと拡張したものであり、**AIモデルの急速な世代交代・性能向上にも陳腐化せずに追従できること**を設計目標とする。

---

## 1. モデル進化に追従するための設計原則

特定のモデル名（固有名詞やバージョン番号）を運用ルールの前提にハードコードすると、数ヶ月ごとの世代交代でガイドラインが陳腐化する。そのため、本リポジトリでは以下の3原則を採用する。

1. **モデル名ではなく「能力階層（Capability Tier）」で業務を定義する**
   - タスクの割り当ては「必要な推論の深さ・不確実性」に基づく抽象ティア（Tier 0〜3）で表現し、具体的なモデル製品名との対応表は末尾の「運用スナップショット」として分離・差し替え可能にする。
2. **「知識の結晶化」によってタスクを下位ティアへ降格させる（Crystallize & Demote）**
   - 未知の設計や複雑な調査は上位ティアで解決し、そこで得られた成功パターンを**「テンプレートスクリプト」「型定義」「不変条件テスト」としてリポジトリに結晶化**する。型とテストが整備された定型作業は、順次下位ティアへ委譲する。
3. **品質ゲート（テスト群）をモデル性能の客観的ベンチマークにする**
   - 「新世代の軽量モデルがどこまで任せられるか」は主観ではなく、ResoWorld の決定論的品質ゲート（`typecheck`, `cross-space-visit-invariants.test.ts`, `dataset-sync-invariants.test.ts`, `build:pages` 等）を初回で安定通過できるかどうかで判定する。

## 2. 能力階層（Capability Tiers）とタスク配分

| Tier | 役割の定義 | 主な担当タスク（ResoWorld での具体例） | 期待する特性 |
| :--- | :--- | :--- | :--- |
| **Tier 0**<br>**Deterministic** | 決定論的コード・検証基盤 | ・ハッシュ計算、ID生成、参照整合性チェック<br>・`sync:dataset` による三ファイル双方向同期<br>・TypeScript 型検査、Vitest 不変条件テスト、`build:pages` | 再現性 100%（AI を使わずコードで保証） |
| **Tier 1**<br>**Fast / Execution** | 高速・定型実行モデル | ・既存スポットID、座標、Claim の調査・一覧取得<br>・文言・ラベル調整、エイリアス追記<br>・定型コマンド実行（`typecheck` / `test` / `build`）とエラー報告<br>・Git コミット・プッシュ等のリリース定型作業<br>・テンプレートに基づく単発スポット更新 | 応答速度・低コスト・指示通りの正確なツール実行 |
| **Tier 2**<br>**Standard / Synthesis** | 標準・構造化統合モデル | ・**方法Cによる旅行記・考察の構造化取り込み**（原本の匿名化・抽象化、Spot / Claim / Connection / Frontier Suggestion の生成）<br>・既存 LENS パックへのノード・アサーション追加と対応テスト追記<br>・通常レベルのバグ修正やリファクタリング | テンプレート踏襲能力・文脈読解・根拠と推測の分離 |
| **Tier 3**<br>**Deep Reasoning / Architect** | 高推論・設計モデル | ・単一FSMやカメラ副作用などコア状態設計の変更<br>・三空間（Map / Lens / Frontier）不整合の構造的原因解明（原則⑱）<br>・新規 LENS アーキタイプ（DAG・軌道・マトリクス等）の幾何計算実装<br>・複数史料・異説の学際的統合や新規トピックのゼロからの設計 | 高度な抽象化・型レベル不変条件設計・多層影響分析 |

> **境界の原則**: 迷った場合は「まず **Tier 0**（コード/スクリプト）で解決できないか」を確認し、次に **Tier 1〜2** を検討し、構造設計や原因究明が必要な局面のみ **Tier 3** を投入する。

## 3. モデル進化への追従プロトコル（昇格・降格ルール）

モデルの進化やツール環境の変化に合わせて、以下のサイクルで担当境界を継続的にアップデートする。

### A. 段階的降格（Demotion）— 軽量モデルの進化を取り込む
新しい世代の軽量モデル（または高速モード）が利用可能になったら、以下の手順で適用範囲を広げる。

1. テンプレートが確立済みの **Tier 2 作業**（例：1訪問記のインポートスクリプト作成）を **Tier 1 モデル** で試行する。
2. 以下の客観的基準をすべて満たす場合、その作業カテゴリの標準担当を **Tier 1 へ正式に降格** する。
   - [AGENTS.md](../AGENTS.md) の「もぐらたたき禁止（原則①）」「実態と状態の混同禁止（原則⑨）」に違反していない。
   - 生成された Claim で「観察事実」と「史料批判・仮説」が分離されている。
   - `cross-space-visit-invariants.test.ts`（未訪問候補が誤って訪問済み汚染されないこと等）を含む全テストと `build:pages` が1〜2ターン以内に通過する。

### B. 異常検知時のエスカレーション（Escalation）— 品質劣化を防ぐ
軽量・標準モデルで作業中に以下の兆候が現れた場合は、無理に試行回数を重ねず **即座に Tier 3 へ切り替える**。

- テストの失敗に対し、既存構造を直すのではなく `if (name.includes(...))` のような場当たり分岐を足し始めた。
- 既存のドメイン不変条件（`observed_place` の付与ルール、三空間バインド等）を誤ってバイパス・改変しようとした。
- 同じビルド・型エラーを2回以上連続して解決できない。

エスカレーション先の Tier 3 では、目先の修正だけでなく**「なぜ下位ティアで誤りが起きたか」を型・テスト・テンプレートの改善（知識の結晶化）で封じ込める**ことを完了条件とする。

## 4. 日常運用における実践ワークフロー

### パターン①：チャット開始時のモデル選択（おすすめ）
- **日々の旅行記・考察の取り込み（方法C）**:
  - 原本（スマホ／Google Drive）をチャットへ添付して構造化・匿名化する通常作業は、**Tier 1〜2 相当の軽量・高速モデル** で開始する。
  - 参考テンプレート例：[scripts/import-fukuoka-city-museum-2026-11-14.mjs](../scripts/import-fukuoka-city-museum-2026-11-14.mjs)
- **設計・複雑な不具合調査・大規模LENS新設**:
  - **Tier 3 相当の高推論モデル** で開始する。

### パターン②：高推論モデル（Tier 3）起動時のサブエージェント委譲
高推論モデルで会話を開始した（あるいは設計途中で定型作業が発生した）場合は、メインモデルの推論枠と時間を節約するため、作業を明示的に分離する。

- **メインエージェント（Tier 3）の責務**: 要件整理、データ構造・設計方針の決定、最終コードレビュー。
- **サブエージェント（Tier 1 相当モデル指定）の責務**: コードベース内のID調査、テンプレートに沿ったスクリプト生成、テスト・ビルド実行、ログ確認。
